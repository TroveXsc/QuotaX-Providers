# Provider 发布流程

状态：已接入发布工具与自动工作流，待首轮真实签名发布及原生闭环验证。App 与真实账号验收按客户端证据单独记录。

## 单一维护入口

维护者在私有源仓库修改 Provider 定义及其合成测试。本仓库的目录和发布附件均为生成产物，不手工修改文件摘要、兼容要求或签名，不复制一套 Schema 或执行器实现。

## 发布顺序

1. 修改目标服务的 `provider.json`，更新版本及受影响测试；稳定 providerId 和指标身份按兼容规则维护。
2. 使用锁定的共享合同与执行器运行结构、引用、能力和执行回归。
3. 根据准确的 Provider 字节计算 SHA256 和长度，生成版本化 ReleaseManifest 并签名。
4. 创建 Release 草稿，上传全部附件，核对内容后发布为不可变版本。
5. 生成并签名 beta 的完整 Catalog，保留未变化的服务条目，递增该通道的发布序列；将 Catalog、准确 Manifest 元数据和完成回执作为同一个 Git 提交发布到 main。
6. 完成候选版本验证后，维护者在私有仓库工作流中显式推广到 stable；相同准确正文和有效 Manifest 可复用不可变附件。

各通道串行发布。被目录引用的文件先发布，目录最后发布；已发布文件不覆盖，修复和恢复旧的正确规则均通过新的版本及序列完成。每周自动续签只续签各通道已发布的定义，不将新的 beta 源配置自动推广到 stable。

## 合同与权限

Catalog 和 ReleaseManifest 使用现行合同的 `schemaVersion`、`canonicalization`、`signed`、`signatures` 封装。Ed25519 签名与文件 SHA256 分别验证发布来源和准确字节，不能相互替代。

签名私钥和仅限本公开仓库的 SSH deploy key 保存在受信任的私有发布环境。该密钥只推送经过签名的 JSON 计划；公开 Actions 作业使用限于自身仓库的临时 GITHUB_TOKEN 上传附件。公开测试样例密钥不作为正式或内部发布身份；用户 API Key、OAuth Token、授权 code 和真实敏感响应不进入发布产物。

App 不携带本仓库或私有源仓库的写入凭据。下载文件只能声明已支持的能力，不能新增宿主回调注册、执行机制或原生渲染器。

计划写入 `publish/<计划ID>` 分支的 `inbox/`。该分支先触发只读权限的提交作业，再由默认 main 上的 `workflow_run` 启动具有写权限的发布作业；特权 YAML 与执行工具均固定到默认主干提交，仓库、push 事件、成功状态、分支与 SHA 均须匹配，计划分支只提供准确 JSON。SSH write key 本身属于公开仓库维护权限，这不构成针对维护者的权限沙箱；App 的内置信任与验签独立保留。

完成状态以 main 已提交的 `receipts/<计划ID>.json` 为准，回执绑定通道、Catalog 摘要与序列。失败时重试同一冻结计划，准确附件可复用；已完成的操作即使后来目录推进，仍可从其准确回执恢复成功。未完成且目录已被另一发布推进时，旧计划报冲突而不覆盖新目录。

若存在已上传但未入目录的孤儿附件，先恢复原 operation 或原工作流；新操作不会覆盖已有 Tag，也不能靠换操作绕过附件冲突。确认旧操作没有未恢复外部副作用后，才能从最新 main 建立新计划。

Release Tag 为 `<服务>-v<releaseVersion>-r<publicationSequence>`。`rN` 允许准确正文不变时续签签名清单；同一个 Provider 版本的不同正文被拒绝。`metadata/manifests/<SHA256>.json` 保存已发布 Manifest 的准确字节，用于审计、去重和防回退。共享 SDK 与第三方许可位于 `tools/generated/`，由私有源仓库生成并审查更新，不能手工补丁。

## 与 App 发版分离

Provider 的独立发布不自动触发 TestFlight 上传。App 发版时，通过锁定清单从已验证 Provider 产物生成随包离线基线；远程更新走同一个编译、执行和渲染路径。

客户端在暂存、验证和更新影响检查通过后，才以受控事务切换活动版本与代次。保留旧值、来源和原采集时间；App 与 Widget 的迟到结果仍须通过当前版本及 fence 检查。

发布记录须区分：文件已发布、客户端已下载、验证通过、已激活，以及真实账号／真机验收完成。
