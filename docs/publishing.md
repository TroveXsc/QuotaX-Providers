# Provider 发布流程

状态：实施约定。发布工作流、正式签名材料和 App 更新器尚未接入。

## 单一维护入口

维护者在私有源仓库修改 Provider 定义及其合成测试。本仓库的目录和发布附件均为生成产物，不手工修改文件摘要、兼容要求或签名，不复制一套 Schema 或执行器实现。

## 发布顺序

1. 修改目标服务的 `provider.json`，更新版本及受影响测试；稳定 providerId 和指标身份按兼容规则维护。
2. 使用锁定的共享合同与执行器运行结构、引用、能力和执行回归。
3. 根据准确的 Provider 字节计算 SHA256 和长度，生成版本化 ReleaseManifest 并签名。
4. 创建 Release 草稿，上传全部附件，核对内容后发布为不可变版本。
5. 生成并签名 beta 的完整 Catalog，保留未变化的服务条目，递增该通道的发布序列。
6. 完成候选版本验证后，按正式通道的信任策略生成正式发布文件并更新 stable Catalog。

各通道串行发布。被目录引用的文件先发布，目录最后发布；已发布文件不覆盖，修复和恢复旧的正确规则均通过新的版本及序列完成。

## 合同与权限

Catalog 和 ReleaseManifest 使用现行合同的 `schemaVersion`、`canonicalization`、`signed`、`signatures` 封装。Ed25519 签名与文件 SHA256 分别验证发布来源和准确字节，不能相互替代。

签名私钥与上传凭据保存在受保护的发布环境。公开测试样例密钥不作为正式或内部发布身份；用户 API Key、OAuth Token、授权 code 和真实敏感响应不进入发布产物。

App 不携带本仓库或私有源仓库的写入凭据。下载文件只能声明已支持的能力，不能新增宿主回调注册、执行机制或原生渲染器。

## 与 App 发版分离

Provider 的独立发布不自动触发 TestFlight 上传。App 发版时，通过锁定清单从已验证 Provider 产物生成随包离线基线；远程更新走同一个编译、执行和渲染路径。

客户端在暂存、验证和更新影响检查通过后，才以受控事务切换活动版本与代次。保留旧值、来源和原采集时间；App 与 Widget 的迟到结果仍须通过当前版本及 fence 检查。

发布记录须区分：文件已发布、客户端已下载、验证通过、已激活，以及真实账号／真机验收完成。
